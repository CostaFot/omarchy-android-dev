## The helper contract

```
/usr/bin/python3 bin/omarchy-android-dev [--settings '<json>'] [--serial S] <command> [args]
```

`--settings` carries the plugin's shell.json scalars (`adbPath screenshotDir recordingDir apkDir scrcpyArgs mirrorScreenOff notify deviceNotifications confirmUninstall showSystemApps`); unknown keys are ignored, defaults are in `cli.SETTING_DEFAULTS` and must match `manifest.json`, `Store.helperSettingKeys`, `Panel.settingsDefaults` and the panel's `settingsTextKeys`/`settingsBoolKeys` (`tests/test_manifest.py` pins the values, the schema order and the form's ids); each value takes the type of its default (`coerce_setting`), so a boolean given as the word `"false"` is false. `--serial` wins over the remembered device.

Envelope on every document: `schema_version:1, command, ok, error, generated_at, adb:{path, source, path_text, source_text, text}` (`text` is the hub's line, `~/Android/Sdk/platform-tools/adb · found in ~/Android/Sdk`; all `null` without adb), then the payload; device commands add `selected`. `error` is `{code, message, stderr?}` with codes `no_adb no_device many_devices unauthorized offline adb_failed bad_args timeout too_much_output state_corrupt no_tool internal` (`no_tool`: scrcpy, the emulator, the terminal launcher, wl-paste or qrencode is missing or exited at once). **A document can carry `ok:true` and an error at the same time** (`state_corrupt` rides with a good answer); consumers treat "has data" and "has error" independently. `notice` is the one-line human result the panel shows and a notification carries.

## The QML side

- **Service.qml** is an `Item` (a `QtObject` has no default property for the `Process`), created by the shell with `shell manifest omarchyPath` injected, only while the plugin is enabled (`shell.qml _syncServices`), and destroyed on disable. It owns the one `Store`, the tracker, the notifications and the one `IpcHandler { target: "costafot.android-dev" }` (two handlers on one target is a shell warning and the second is ignored; `Panel.qml` sets `manageIpc: false` for that reason). Bar widgets call `registerHost(widget)`/`unregisterHost` (one per monitor); `hostSettings` is the first host's `settings` (the shell injects settings only into bar widgets) and reaches the Store and the tracker as `--settings`; with no host the helper runs on its defaults. Panel verbs go through `shell.summon/hide` so the widget on the focused monitor answers; `page` uses the open host, else the first.
- **The tracker** is `Process { stdout: SplitParser }` running `sh -c 'exec "$0" "$@"' /usr/bin/python3 <pluginDir>/bin/omarchy-android-dev --settings … track`. Every line is parsed on its own (`applyTrackerLine`: a `devices` event replaces `store.devices`/`selected` and resets the backoff, an `error` event sets `trackerError`; `no_adb` also blanks `store.adbInfo` so the hub shows the note). `onRunningChanged` to false restarts it after `trackerBackoffMs` (5 s doubling to 60 s), or at once when `trackerRestartPending` (a `settingsJson` change, through a `Connections` on the store). `stopTracker()` sends SIGTERM (`tracker.signal(15)`); the helper forwards it to adb. **The shell ends the helper with SIGKILL on destroy**, which no handler can forward: seen 2026-09-05 as an orphaned `adb track-devices` after `omarchy plugin disable`; fixed by `PR_SET_PDEATHSIG` on the adb child (`adb.popen`, `preexec_fn=die_with_parent`) and on the helper itself (`track`), tested by `test_track_helper_killed_outright_takes_adb_with_it`. The producer-side cap for the stream is the helper's own (32 devices, 256-character fields); a line over 64K characters is dropped as `too_much_output`.
- **The recorder** is a second `Process { stdout: SplitParser }` in the service running `… --settings … record`, started by `startRecording()` (`recorder.command` assigned fresh each time, one recording per shell), stopped by `stopRecording()` = `recorder.signal(2)` (SIGINT, what Ctrl-C does in a terminal; the helper handles SIGTERM the same way). `applyRecorderLine`: a `recording` event sets `recording` and `recordingStartedAt` (a 1 s `Timer` bumps `recordingSeconds` while it runs; `elapsedText(s)` formats `m:ss` for the panel and the tooltip); the final line goes through `store.handle(text)` like any run, so its `notice` is the panel's and its `error` is `lastError`, and a failure gets a notification here (the helper sends its own for the saved file). `recorderExitFallback` (300 ms after the process ends) catches a run that printed no final line (could not start, killed): an urgent "ended without an answer" notice. `recordingStopping` is true between the signal and the answer; the Capture page shows "Saving the recording…" then. `statusJson` carries `recording:{active stopping seconds device_path}`. On destroy the recorder gets SIGINT but the shell SIGKILLs it right after; PDEATHSIG ends the adb client, screenrecord finishes the file, and the mp4 stays on the device at `/sdcard/omarchy-android-dev-<stamp>.mp4` (the documented limitation; `IDEAS.md` has the pull-the-leftovers idea).
- **The pairer** is a third `Process { stdout: SplitParser }` running `… --settings … pair qr`, started by `startPairing()` (one session per shell), cancelled by `stopPairing()` = `pairer.signal(2)`. `applyPairerLine`: the `pairing` event sets `pairing`, `pairingQr` (the PNG's path), `pairingName`, `pairingWindow` and starts the 1 s countdown (`pairingSeconds`); the final line goes through `store.handle(text)` like any run (its `devices` and `selected` land at once, its `notice` is the panel's), with a "Paired with …" notification here and the error as one on failure. A cancelled session prints nothing by design, so `pairerExitFallback` (300 ms) is where "Pairing cancelled" comes from (and "ended without an answer" when it was not asked to stop). `statusJson` carries `pairing:{active stopping seconds window qr_path name}`. On destroy the pairer gets SIGINT and the shell SIGKILLs it after; the helper's adb children carry PDEATHSIG and the PNG stays until the next session sweeps it.
- **Device notifications** (`notifyDevices`): skipped on the `initial` frame and when `notify` or `deviceNotifications` is off; a serial in state `device` that was not ready on the previous frame (`knownReady`) → "Android device connected", `removed` → "Android device disconnected", `unauthorized` → "Android device needs authorising" once per serial while it stays so. "Connected" means *became ready*, not *appeared*: an emulator appears as `offline` with no model (the first toast said `emulator-5554`, seen 2026-09-05) and is ready a minute later with its AVD name; a phone appears ready or `unauthorized`. Labels for a removed device come from `knownLabels`, which keeps the label from the last frame where the device was `device`: an emulator on its way out passes through `offline`, where `emu avd name` no longer answers and the label falls back to the model. Sent as `Quickshell.execDetached([omarchyPath + "/bin/omarchy-notification-send", "--app-name", "Android Dev", "-g", glyph, headline, body])`, argv only.
- **Store.qml** is Markets' Store (`run(args, onDone, stdinText)`: `stdinText`, when given, sets `proc.stdinEnabled` before the start and is written in `onStarted`, then blanked and stdin closed, the kit's network panel's pattern for a secret; a queued run keeps its text; the pairing code is the one user, one `Process` through `/bin/sh -c 'exec "$0" "$@"' /usr/bin/python3`, `pendingRuns` (a queue: an `isRead` run, the seven page reads and `apk list`, replaces any read waiting, since the later one answers for both; every other run is an action and waits in order; `maxPending` 8, past which the newcomer is refused with a notice; a timed-out run drops the queue behind it and its timeout text counts the dropped requests; `runNext` dequeues through `Qt.callLater`), `collectorDone`+`processDone` with the 300 ms `exitFallback`, 1 MiB `StdioCollector` tripwire, `helperBudgetSeconds` 60 as `OMARCHY_ANDROID_DEV_TOTAL_BUDGET` through `proc.environment` assigned in `run()`, `killTimer` SIGTERM 10 s after the budget then `killFallback` SIGKILL 5 s later) plus **`runGen`**: every run increments it and each timer carries the generation it was armed for, so a stale timer from a killed run never fires into the next one; a `timedOut` run is reported as `timeout` whatever it printed. Merge rule in `handle()`: `adb` → `adbInfo` (`path source text`; `adbText` is the string) always; `command:"status"` → `status`; a `devices` array → `devices` + `selected`; `packages` → `packages` + `packagesInfo`; `toggles` → `toggles`; a `command:"apk"` document with `apks` → `apkList`; a `command:"tools"` document with `avds` → `toolsInfo`; a `command:"wireless"` document with `mdns` → `wirelessInfo`; `recent_deeplinks` → `recentDeeplinks`; `last_package` (present, even `null`) → `lastPackage`; a good `command:"package"` → `packageDetails[name]`; a good `app uninstall` drops that package from `packages`; `error` → `lastError`/`lastErrorCode` without blanking anything; `notice` → `showNotice` (3 s), and an `ok:false` error message becomes an urgent notice. `runningCommand` is the first argv word of the run in flight (`""` between runs) so a page can tell its own "Listing packages…" from someone else's run. `applyTrackerEvent(ev)` is the tracker's way in (no queue). `onSelectedChanged` blanks `toggles`: they were read from one device. No polling timer anywhere: the tracker pushes devices, the panel refreshes `status` on open and `r`, `packages` on entering the Apps page, `package PKG` on entering an actions page, `toggles` on entering the Toggles page and after every flip (the flip's document carries all nine), `apk list DIR` on entering the APKs page and 300 ms after the folder box changes, `tools` on entering the Tools page, after a Start or Stop, and whenever the tracker changes the device list while that page is open (an emulator leaves the list a few seconds after `emu kill`, once its snapshot is saved; a started one joins when it boots, 8 s with quickboot here), so a freshly installed scrcpy shows up without a restart and the Running/Stopped rows follow the devices; `wireless` on entering the Wireless page (not its Pair with a code sub-page, which shows nothing from it), on `r`, whenever the tracker changes the device list while the Wireless page is open, and when a pairing session ends. The `connect`, `disconnect`, `tcpip`, `usb` and `pair code` answers carry the fresh device list, so the picker and the page move before the tracker's next frame.
- **`Service.act(args, onDone, silent, stdinText)`** is the one path for everything that changes the device, from the panel and from the IPC verbs alike: `store.run(args, …, stdinText)`, then a notification with the helper's `notice` as the headline and the selected device's label as the body (`store.lastError` when the run failed), skipped for `screenshot` (the helper sends its own), when `notify` is off, or when `silent` is true (the APK page's Install all passes it and sends one `Installed n/m APKs` summary through `service.notify` instead); the panel shows the same notice as its row. IPC action verbs (`launch forcestop clear deeplink flip text clipboard scrcpy avd logcat disconnect tcpip usb`) check the argument shape (`validPackage`: `[A-Za-z0-9_.]`, 256 chars; a URL: no whitespace or control characters, 2 KiB; a toggle name from `toggleNames`; `validText`: printable ASCII, 500 chars; `validAvd`: `[A-Za-z0-9._-]`, 64 chars; `validAddress`: `host[:port]`, IPv4 or a name, 260 chars; `validSerial`: the serial alphabet, 128 chars; `logcat` with no argument follows the whole log, `tcpip`/`usb` with `""` take the selected device) and answer `requested`; the helper validates again and a `bad_args` comes back as an urgent notice and a notification. There is no `pair code` over IPC on purpose: the code would sit on `omarchy-shell`'s argv. `record start|stop|toggle` answers `requested`, `stopping`, `already recording` or `not recording`, and `pair start|stop|toggle` the same words with `pairing`; `page` accepts `hub devices packages deeplink toggles capture apks text tools wireless settings`. `status` answers one JSON line with `version plugin_dir adb settings` (the scalars the store sends the helper, so `omarchy bar set` can be checked live) `devices selected selected_label tracker busy error_code error recording pairing hosts opened page` (`page` is the open panel's, `""` when closed; the widgets expose `page` for it); `help` ends with the settings keys and the `omarchy bar set` form (`test_help_names_every_setting`, and the `page NAME` line is pinned to `Panel.ipcPages`).

## Hard-won constraints — do not re-litigate without re-testing

- **Never crash.** `cli.main` catches `BaseException`; a traceback on stdout would be parsed as garbage by QML and blank the bar. Errors ride inside the JSON. Verified: `bin/omarchy-android-dev bogus; echo $?` → 0.
- **Every adb call goes through `Adb.run`**: absolute binary, argv list, `-s SERIAL` on every device command, `timeout=` (10 s default, 60 s for uninstall, 30 s for screencap, none for `track`), `cap=` (256 KiB default, 1 MiB for `pm list`/`dumpsys`, 20 MiB for screencap). The reader threads stop at the cap and kill the child; `too_much_output` is an error, never a parse. Package names, URLs and paths are single argv entries; the Windows `\"…\"` quoting must not be copied. The one shell script in the tree (`toggles.READ_SCRIPT`) is a fixed string with no device data in it.
- **The failure rule is wider than Windows'**: exit code ≠ 0, or `error:` on stderr, or a stdout line starting `Failure`, `Error:` or `Failed`. `pm clear` on an unknown package prints `Failed` with exit 0; `adb uninstall` prints `Failure [DELETE_FAILED_INTERNAL_ERROR]` with exit 1; both are caught (`shell pm uninstall` exits 0 on failure, which is why `uninstall` uses the host verb).
- **`ensure_server()` runs once per helper run**, under `flock` on `<state dir>/adb-server.lock` (non-blocking loop, 10 s ceiling). Under the lock: a stamp written by another holder within 10 s means skip; a connect to adb's server port that succeeds means skip; otherwise `adb start-server`, then write the stamp. Dori PR #4 is the crash this prevents (two clients at login, one aborts on the busy socket). `test_two_helpers_at_once_start_the_server_once` runs two helpers against a fake that sleeps in `start-server`.
- **Cold-start banner.** The first adb call after boot prints `* daemon not running; starting now at tcp:5037` / `* daemon started successfully` on stdout ahead of its result; `fmt.lines()` drops every line starting with `*`. Fixture `devices_l_coldstart.txt`.
- **`screencap -p` on the foldable emulator prints `[Warning] Multiple displays were found…` ahead of the PNG** (seen 2026-09-05, API 37). `capture.split_png` looks for the signature within the first 4 KiB, keeps the image and returns the text as `warning`. Anything without a signature is `adb_failed` and no file is written.
- **The foreground package** comes from `dumpsys window` `mCurrentFocus=Window{… u0 PKG/ACTIVITY}` (still there on API 37) with `dumpsys activity activities` `topResumedActivity=` as the fallback. `ps -A` rows are matched on the `u0_a*` user and the last column with any `:subprocess` suffix removed, so a package with only a service process counts as Running (Windows compared the raw name and missed those).
- **`dumpsys package PKG` prints the package twice** for an updated system app (the installed copy under `Packages:`, then the stub under `Hidden system packages:`); `parse_package_dump` reads the first section only and stops at the second header. Runtime permissions are the first `runtime permissions:` block (user 0), ended by a dedent.
- **Emulator labels** cost one `adb -s SERIAL emu avd name` per running emulator per `devices` call (5 s timeout, `OK` line skipped). A phone's label is its model with `_` → space. `devices -l` states include `no permissions (…)` with spaces; the parser handles it.
- **Toggles are read in one `adb shell`** (`toggles.READ_SCRIPT`: `api=`, `layout=`, then `namespace:key=value` lines). Animations are on unless `window_animation_scale` is `0`; a `null` setting is "never set" (off for touches/pointer/layout/airplane, unknown for wifi/data/bluetooth). Airplane mode uses `cmd connectivity airplane-mode enable|disable` on API ≥ 30 and `settings put` + the broadcast before that. Layout bounds needs `service call activity 1599295570` after `setprop debug.layout`. Every flip re-reads and returns all nine. **Demo mode** (`demo`) is SystemUI's (`toggles.DEMO_ENTER`: `settings put global sysui_demo_allowed 1`, then `am broadcast -a com.android.systemui.demo -e command enter|clock|notifications|battery|network|network|status …`; off is `exit` and the gate back to 0). AOSP mirrors the shown state into `sysui_tuner_demo_on`; the HONOR phone (Android 16) never writes it, so `on` is either key at 1, and clearing the gate on exit is what makes off read back as off there. That phone honours the battery and notification commands and ignores the clock and the signal ones (seen 2026-09-05); the emulator takes all of them.
- **State files** (`state.py`): the dir is verified on every run (not a symlink, a directory, owned by us, no group/other bits; a failing dir means no state is read or written and `state_corrupt` rides in the envelope); reads open `O_RDONLY|O_NOFOLLOW|O_NONBLOCK|O_CLOEXEC`, `fstat` a regular file under 64 KiB and read through the descriptor; a symlink (`ELOOP`), an oversized or an unparsable file is renamed to `<name>.bak.<ts>` (rename never follows the link) and reported once; writes are `mkstemp` in the same dir (0600, `O_EXCL`), `fsync`, `os.replace`. No `/tmp` anywhere. `packages-<serial>.json` uses `state.file_token()` for the serial (`:` → `_`).
- **The whole run has a budget** (`OMARCHY_ANDROID_DEV_TOTAL_BUDGET`, 60 s): `cli.main` arms `SIGALRM`, the handler raises `cli.Deadline` (a `BaseException`), `dispatch` answers `error.code timeout`; `track`, `record` and `pair qr` disarm it (the QR session has its own 120 s window, and its SIGINT/SIGTERM handlers raise `wireless.Cancelled`, another `BaseException`, so a cancel inside `run_bounded`'s wait kills the adb call in flight the same way). Python runs the handler between bytecodes, so a `proc.wait()` is interrupted but a stuck C call is not: that is what the store's kill timer will be for in 0.2.0.
- **Boolean settings arrive as words too.** `omarchy bar set costafot.android-dev showSystemApps false` without `--json` stores the string `"false"` in shell.json, which is truthy everywhere (seen 2026-09-05: the Apps page kept listing system apps). `cli.coerce_setting` gives every setting the type of its default (`true/1/yes/on`, `false/0/no/off/""`, anything else the default; strings for the paths) and `Store.flag(key, fallback)` does the same in QML; nothing reads a boolean setting any other way.
- **Notifications and the clipboard are optional.** `notify.send` and `notify.copy_file` run `omarchy-notification-send` / `wl-copy` as argv with a 5 s timeout and return False on any failure; the screenshot is already on disk. `notify:false` in the settings silences notifications; nothing else is affected.
- **Nothing is killed by name.** The only children signalled are the ones `Adb.run`, `track`, `record`, `pair qr` and the four QML `Process`es hold; no `pkill`, no `pgrep` outside the tests, no PID files. The helper and its adb children carry `PR_SET_PDEATHSIG` (SIGTERM) because the shell ends a `Process` with SIGKILL when its owner is destroyed. The tests' `pgrep` patterns are anchored to the fake adb's own command line (`^/usr/bin/python3 .*fakeadb\.py …`): a shell whose argv mentions the word (a heredoc through the Bash tool) matched `pgrep -af fakeadb.py` on 2026-09-05.
- **An explicit `adbPath` is an instruction, not a hint.** `adb.resolve` stops at a set `adbPath` that holds no adb and `missing_text` names it; falling through to the SDK's adb hid a typo behind a working plugin and made the S6 acceptance ("No adb at …") impossible. Clearing the setting is how auto-detection comes back.
- **The keys the plan named are taken.** `SUPER + SHIFT + A` is ChatGPT and `SUPER + SHIFT + S` is Google Maps in Omarchy's defaults (`default/hypr/bindings/applications.lua`), and `SUPER + ALT + S` is the scratchpad; the README binds `SUPER + ALT + A` and `SUPER + ALT + C`, both free on 2026-09-05. Bindings here are Lua (`o.bind("SUPER + ALT + A", "Android Dev panel", "omarchy-shell …")` in `~/.config/hypr/bindings.lua`); the `bindd =` conf form is given as the second option. The menu extension file is `~/.config/omarchy/extensions/omarchy-menu.jsonc`; the Capture submenu's id is `trigger.capture`.
- **The emulator is an X11 client with two windows.** Its bundled Qt ships only the `xcb` platform plugin (`Could not find the Qt platform plugin "wayland"` in its log), so under Hyprland it is XWayland: a main window (`_NET_WM_WINDOW_TYPE_NORMAL`, class `Emulator`, initial title `Emulator`, later `Android Emulator - AVD:PORT`) and a toolbar tool window (same class, title `Emulator`, 44x404) that Hyprland floats on its own. Tiled, the main window keeps the phone's aspect and pads the tile grey, and the toolbar sits loose over it. Verified 2026-09-05 with rules added through `hyprctl eval 'hl.window_rule({...})'` (a `hyprctl reload config-only` drops them again): `o.window("^(Emulator)$", { float = true })` floats it into a phone shape (329x731 logical here) with the toolbar hugging its right edge; `center` is a no-op for it because the emulator moves both windows to the position saved in `~/.android/avd/NAME.avd/emulator-user.ini` right after map (so a class-only rule that also matches the toolbar does no harm). scrcpy is a native Wayland window and `center` works there. The emulator launcher rewrites `QT_SCALE_FACTOR` to `none` in its own environment, so the plugin cannot scale its UI for a HiDPI monitor through the environment; the README says to resize the window instead. Not a plugin matter beyond the README: window rules belong to the user's Hyprland config, and the helper never runs `hyprctl`.
- **The IPC verb for the developer toggles is `flip NAME`, never `toggle`**: that name opens and closes the panel (the kit's convention, and `IpcHandler` has one function per name). The helper's command stays `toggle`.
- **The shell's children inherit an ignored SIGINT.** Quickshell starts its `Process`es with SIGINT in the ignored set, and an ignored disposition survives exec while a handled one resets to default. The helper installs its handlers (`track`, `record`; `pair qr` through `wireless.arm_cancel()` from `dispatch`, ahead of the server check and the mDNS check: found in the 1.2.0 review, a `pair stop` in that window was dropped) *before* it spawns adb, `die_with_parent` (every `adb.popen` child's preexec) puts SIGINT back to `SIG_DFL`, and the recorder stops its adb client with SIGTERM anyway. Seen 2026-09-05: `record stop` from the service did nothing because the adb child had inherited `SIG_IGN` (`grep SigIgn /proc/PID/status`, bit 0x2) while the same code worked from a terminal. Nothing may rely on SIGINT reaching a grandchild.
- **Stopping a recording is a hang-up, not a kill.** Ending the adb client closes its socket; adbd sends the remote shell SIGHUP; screenrecord handles SIGHUP and writes the `moov` atom. Verified 2026-09-05 on API 37: the device file stopped growing within 0.5 s and matched a `--time-limit` run byte for byte in shape. The helper waits for two equal non-zero `stat -c %s` reads before pulling; never pull a file that is still growing. There is no `record.json` and no `record stop` in the helper: a terminal recording ends with Ctrl-C, the service's ends with the signal to its own Process (no PID files, invariant below).
- **Detached launches are left alone.** `tools.launch` starts scrcpy, the emulator and the logcat terminal with `start_new_session=True`, stdin/stdout/stderr on `/dev/null` (a child holding the helper's stdout would keep the store's collector waiting for EOF; `test_launched_tools_get_no_pipes_from_the_helper` pins it), SIGINT back at `SIG_DFL`, **no** PDEATHSIG (they must outlive the helper), wrapped in `uwsm-app -- …` when it is on PATH (Omarchy's own launchers do the same; `OMARCHY_ANDROID_DEV_LAUNCHER=""` bypasses it in tests). That wrapper matters: the shell runs inside the `wayland-wm@hyprland.desktop.service` cgroup, and a child spawned from it plainly would die with a restart of that unit; verified 2026-09-05 that an emulator started from the Tools page sits in its own `app-….scope` under `app.slice` (`cat /proc/$(pgrep -f 'qemu-system.*-avd Medium_Phone')/cgroup`). The helper waits `LAUNCH_GRACE` (0.5 s) and reports `no_tool` `X exited at once (code N)` if the tool died, otherwise it never looks again. Nothing launched here is signalled by the plugin; an emulator stops through `adb emu kill`, which it handles itself. `emulator -list-avds` answers in milliseconds here, but the call has a 15 s deadline like everything else. **scrcpy gets `ADB=<the resolved adb>` in its environment** (`launch(argv, name, env=…)`): the `scrcpy` package depends on `android-tools`, whose `/usr/bin/adb` would otherwise be the one scrcpy picks off PATH, and a client of another protocol version kills the running server and takes the tracker's `track-devices` with it. Verified 2026-09-05: `/proc/<scrcpy pid>/environ` carries the SDK path and its adb child is `~/Android/Sdk/platform-tools/adb -s emulator-5554 shell … scrcpy-server.jar …`; `test_scrcpy_is_pointed_at_the_helpers_adb` pins it.
- **`input text` is one line of printable ASCII.** `text.check` refuses anything else (`bad_args`, with the reason); `text.encode` turns spaces into `%s` (input's own escape) and `shlex.quote`s the result, because adbd runs the joined arguments through the device shell before `input` sees them (`test_send_is_one_argv_entry`: `rm -rf / ; echo` arrives as `'rm%s-rf%s/%s;%secho'`). A literal `%s` in the text becomes a space on the device; documented, not worked around. The clipboard is read with `wl-paste --no-newline -t text`: without `-t text` an image on the clipboard came back as PNG bytes (seen 2026-09-05, a screenshot from an earlier test), with it wl-paste refuses (`not available as requested type`) and the helper says `The clipboard does not hold text`.
- **`adb install -r -t`**: `-t` lets a debug build marked `testOnly` install (Windows used `-r` alone). The install is the host verb, so a `Failure [INSTALL_FAILED_…]` lands on stderr with exit 1 and `apk.failure_text` cuts that bracket out for the row. Install all is sequential from the panel, one helper run per file, because one run has one 60 s budget and a 70 MB debug APK needs a few seconds each.
- **A run that hits its budget kills the adb call in flight.** `run_bounded` catches any `BaseException` escaping `proc.wait()` (the alarm's `Deadline`, a Ctrl-C), terminates the child and re-raises; before 0.5.0 an `adb install` interrupted by the alarm went on to finish unseen.
- **No string in the tree names a privilege-escalation, package-manager, service-manager or clone-and-run command** (the seven tokens are in the plan file's invariant 17; the marketplace baseline flags each as a capability and a maintainer then has to rule on it). Say "install the `android-tools` package or the SDK platform-tools" without a command. This sentence is worded the way it is for the same reason.
- Formatting is Python's job (`fmt.py`: labels, `on`/`off`, sizes, paths with `~`, the device `detail` line); QML renders strings and never builds one from device data (the hub appends only literals and counts). Every field is cut at 256 characters with `\r`, ANSI sequences and control characters removed; lists are capped (devices 32, packages 4000, permissions 512, AVDs 64, APKs 200, recent deep links 10, mDNS services 32).
- The manifest's `version` is the single source of truth (`androiddev.plugin_version()`); bump it with the CHANGELOG in the same commit. The manifest `defaults` must equal `cli.SETTING_DEFAULTS` and the schema must list the same keys in the same order (`test_manifest_defaults_match_the_helper`).
- **Glyph escapes through the tools.** Any `\uXXXX` typed into a tool call arrives as the character itself and a PUA character is then dropped (the Write tool, 2026-09-05) or kept as the literal character (the Edit tool, later the same day), so the file ends up with `""` or with a raw glyph; an `old_string` that spells an existing `\uXXXX` still matches. Writing QML through a Python script, spell the escape without typing it: a placeholder such as `@u{f205}` expanded with `chr(92) + "u" + hex`, or reference an existing table (`kindGlyphs.wifi`, `wirelessGlyphs.qr`). Check with `grep -c 'icon: ""'` and a scan for literal U+E000–U+F8FF characters afterwards.
- **The pairing code never touches an argv.** From the panel it goes `filterField` → `act(…, stdinText)` → `Store.run` (`proc.stdinEnabled`, `write()` in `onStarted`, stdin closed) → the helper's stdin (`wireless.read_code`, one line, a 5 s `select` so a silent pipe is `bad_args` and not a hang) → an `os.pipe()` as `adb pair`'s stdin (`Adb.run(stdin=)`). The IPC surface has no `pair code` verb for that reason; a terminal pipes it (`printf '123456\n' | … pair code ADDR`). The QR payload takes the same road into qrencode. `tests/test_wireless.py` pins the fake's log line `["pair", ADDR, "<stdin>123456"]` and that the digits are in no other argv element.
- **The QR payload is a Wi-Fi-credential string by format** (`WIFI:T:ADB;S:<name>;P:<password>;;`, what Android's `AdbQrCode` parses and `enablePairingByQrCode` takes). A camera app or Google Lens reads it as an SSID and password and tries to join a network that does not exist (another plugin's author watched the phone drop off its Wi-Fi); the panel and the README say to scan it from Developer options › Wireless debugging › Pair device with QR code and nowhere else. The phone advertises `_adb-tls-pairing._tcp` under the `S:` name after the scan; the helper matches the instance name exactly (a vendor prefix would need `endswith`; not seen yet).
- **`adb connect` exits 0 on failure; `adb pair` prints `Failed: …` and may too.** Success is the text (`connected to `, `already connected to `; `Successfully paired to`), the cold-start banner ahead of it is dropped by `fmt.lines`, and the call has its own 10 s deadline because adb's TCP timeout is minutes (a phone that drops packets, see the VPN note, is a `timeout` document in 10 s and nothing more). After a good `pair`, adb writes the phone's GUID to `~/.android/adb_known_hosts.pb` and its server auto-connects to that phone's `_adb-tls-connect._tcp` service whenever it is on the network (`ADB_MDNS_AUTO_CONNECT`, known hosts only), so the tracker shows the `ip:port` entry without a `connect` from us; Android picks a new port every time Wireless debugging is toggled and the same mechanism finds it. `adb server-status` shows `mdns_enabled: true` and `mdns_backend: LIBADBMDNS` on the SDK adb (37.0.1); Arch's `android-tools` build answers `adb: mdns is not supported by this version of adb.` to `mdns check`, so the QR path degrades to a note and the code path stays (the terminal still has `connect ADDR`).
- **A LAN-isolating VPN looks like a dead phone.** Seen 2026-09-05: `tcpip 5555` on the HONOR phone succeeded (`getprop service.adb.tcp.port` → 5555) and `ip route` gave `192.168.1.3` on `wlan0`, but `connect`, `nc -z … 5555` and `ping` from the desktop all timed out: NordVPN was connected with LAN Discovery off (`nordvpn settings`) and drops LAN traffic. `usb` put the phone back (`0`). On 2026-09-06 Costa had `nordvpn set lan-discovery on` run (the VPN stays connected; the plugin never touches it): ping answered, `tcpip` connected in 1.7 s, `usb` put the phone back, and Costa paired it by QR code from the panel, after which adb attached it on its own as `adb-AQCK025731000692-WBgDVa._adb-tls-connect._tcp` (no trailing dot; `MDNS_SERIAL_RE` takes both). The phone runs NordVPN too (`tun0`, a full-tunnel route, `bypassable=false`) and still answers on its wlan0 address: Android replies on the interface a connection came in on. Two phone-side traps seen the same day: `settings get global adb_wifi_enabled` read 1 while `persist.adb.tls_server.enable` and `service.adb.tls.port` were empty and `dumpsys servicediscovery` had no adb registration (the switch reads on, the server is off, nothing on mDNS: toggle Wireless debugging off and on), and a phone asleep (`dumpsys display` `mScreenState=OFF`) filters multicast in its Wi-Fi chip and answers no mDNS query (`input keyevent KEYCODE_WAKEUP` first). The README's Requirements and FAQ say so.
- **`omarchy-shell` passes every declared argument or refuses the call** (`Too few arguments provided (1 required but 0 were provided.)`), so an IpcHandler function with a `string` parameter cannot be called bare: `pair` takes `start|stop|toggle` like `record`, and `tcpip`/`usb` take `""` for the selected device. An IpcHandler function named `connect` is fine (no clash seen with qmllint or the shell).

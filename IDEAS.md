# Ideas

Backlog, not commitments. Dead ideas stay here marked as such so they are not re-pitched. The 1.0 roadmap itself is in `AGENTS.md`; this is what comes after it, or what was left out on purpose.

## From the Windows wishlist and the scaffold's open questions

- **Wireless debugging**: done in 1.2.0 (`wireless.py`: QR pairing through `adb mdns services`, pairing by code with the code on stdin, `connect` judged by its text, `tcpip`/`usb`). The *Connect to an address* page and the recent addresses were removed in 1.3.0 (dead: Costa did not want a typed-address path; a paired phone reconnects on its own and the *Seen on the network* rows cover the rest; the helper's `connect ADDR` is the terminal's). Left out on purpose: `pair` with the code over IPC (dead: the code would sit on `omarchy-shell`'s argv; a terminal pipes it to the helper), bracketed IPv6 addresses (`devices.SERIAL_RE` cannot show one), a *Forget* row (adb has no un-pair; the phone's *Paired devices* list and `~/.android/adb_known_hosts.pb` are the two sides), scrcpy's own `--tcpip` (dead: the plugin does tcpip+connect itself so the tracker sees the entry and the selection moves), avahi as a fallback for an adb without mDNS (the code and address paths need no discovery). Open: a note on the Wireless page when the phone is on a VPN or the desktop's VPN isolates the LAN (seen 2026-09-05: NordVPN with LAN Discovery off dropped everything to the phone, ping included; the helper only sees timeouts).
- **Non-ASCII text** for Send text: Android's `input text` is ASCII only. ADBKeyboard (a broadcast to `ADB_INPUT_TEXT` with base64) is the usual answer and needs an APK on the device; a `bad_args` with a plain message is what 1.0 does (0.5.0). A literal `%s` in the text becomes a space on the device (input's own escape); nobody has asked for a way around it.
- **Split APKs** (`.apks`, `.xapk`, `adb install-multiple`) in the APK manager. 1.0 installs single `.apk` files.
- **Recent APK folders** in the folder box (the plan's `recent_apk_dirs`): 0.5.0 prefills the `apkDir` setting and keeps the typed folder only while the page is on the stack. Would be one more list in `state.json`, like the recent deep links.
- **Logcat for a package that is not running**: 0.5.0 refuses (`pidof` finds nothing) and says to launch it first. Launching it and then following its pid, or `logcat` with a `--regex` on the package name as a fallback, would be friendlier.
- **scrcpy's window and the emulator's on Hyprland**: the Tools page launches both through `uwsm-app`; the float rules for the `Emulator` class and scrcpy's `--window-title "Android Dev"` are in the README since 1.0.0 (the emulator's without `center` since the check on 2026-09-05: it moves its windows to its own saved position after map). Done as far as the plugin goes; setting the rules itself would mean writing into `~/.config/hypr`, which it does not do.
- **Pull shared preferences** (`run-as PKG cat shared_prefs/*.xml`) for a debuggable package; a page under the package's actions.
- **Global per-action favorites** as on Windows (star "Launch" for every package). Dead, 2026-09-05: replaced by the last package per device and recent deep links.
- **Keep the panel open after an action** (`keepOpen` on Windows). Dead: the panel stays open by design.

## The 1.x slots (each is an `androiddev` module, a panel page and IPC verbs)

- **Forwarding**: `adb forward`/`reverse` list, add, remove. RN, Flutter and local-API work need it constantly; three adb calls.
- **Tweaks**: dark mode (`cmd uimode night yes|no`), font scale, density and size overrides (`wm density`, `wm size`), locale. Reads current state like Toggles; pairs with Capture.
- **Device info**: model, API level, battery (`dumpsys battery` `level:`), IP, screen (`wm size`), memory (`/proc/meminfo`), disk (`dumpsys diskstats` `Data-Free:`), Wi-Fi SSID and RSSI (`dumpsys wifi`), brightness (`settings get|put system screen_brightness`), foreground activity. One batch; hub header material.
- **Wake and hardware keys**: `input keyevent KEYCODE_WAKEUP|BACK|HOME|APP_SWITCH|POWER|VOLUME_UP|VOLUME_DOWN` as a row group.
- **Reboot**: normal, recovery, bootloader; `adb root`. A stepping stone to fastboot (`adb tcpip` moved to the Wireless page in 1.2.0).
- **Files**: drop-to-push, pull to Downloads. The panel already handles paths for APKs.
- **Bug bundle**: screenshot plus filtered logcat plus `bugreport` zip, one Capture row.
- **Emulator console through `adb emu`** (no telnet, no auth token): battery level and charging (`emu power capacity`), GPS fix (`emu geo fix`), calls and SMS (`emu sms send`), network speed and latency (`emu network speed`), rotate, snapshots. One helper verb.
- **AVD management**: create, wipe, cold boot, snapshot load. Extends Tools.
- **Fastboot**: flash, unlock, boot image. Same USB device; the tracker already sees the mode change.
- **Dev loop**: watch a build output directory, install on change, launch, filtered logcat.
- **Fan-out**: run an action or an install on every attached device. Free once every call takes a serial.
- **Agent driver**: a documented stable CLI plus `uiautomator dump`, tap and type by resource id, so a coding agent can drive the app without a screenshot loop. The JSON helper is already the right shape.
- **Maestro**: a Flows page. Find `maestro` (PATH, `~/.maestro/bin`), report it in `status.tools` next to scrcpy; scan a settings-configured directory or the cwd's `.maestro/` for `*.yaml` flows, run one against the selected device (`maestro --device SERIAL test FLOW --format junit --output FILE`, parse the XML for pass/fail per flow and the failing step), the result as the notice and a notification, recent flows kept like recent deep links; `r` re-runs the last one. IPC `flow PATH` so a Hyprland keybinding runs the smoke flow of whatever is being worked on. Rows for `maestro studio` (a browser tab on `localhost:9999`, the device picker in the tool's own UI) and `maestro record FLOW` (an mp4 of the run, next to Capture). `maestro hierarchy` prints the view tree as JSON, a better UI dump for the agent driver than `uiautomator dump`. Fan-out is the obvious "fun" one: the same flow on every attached device at once, one notification per result. Caveats: a JVM app installed by its own script, so `tools.maestro` may be missing with everything else present; a run lasts minutes, longer than the 60 s helper budget, so it wants the tracker's shape (streaming, no alarm) or a detached run with the result read from the junit file; the first run installs `dev.mobile.maestro` and `dev.mobile.maestro.test` on the device, which then show up in the package list (hide them, or tag them); it forwards port 7001, so two runs on one serial collide; the terminal output is colored and chatty, only the junit file is worth parsing; failure screenshots land in `~/.maestro/tests/`, worth a `Show` row.
- **A full-screen `panel` kind** for a logcat or picker surface that outgrows the popup.

## Open findings from the 1.2.0 review (2026-09-06)

An eight-angle review of the wireless commit (`e5a0e72`). The first two findings were fixed in 1.3.1 (`8d13ec4`: the mDNS-named serial as a Wi-Fi device, the QR session's cancel armed first); the recent-addresses regex went with the connect page in 1.3.0. The rest are open, in the order they are worth fixing. Each is verified against the code, not guessed; the line numbers are as of 1.3.1. Tick them off here (or move them to the CHANGELOG) when done.

1. **"Esc does too" is false** (`Panel.qml:649`). Escape is the generic `pop()` on every page and nothing on that path calls `service.stopPairing()`, so the user lands on the hub while the session keeps polling for up to two minutes with the password PNG on disk, and a phone that scans meanwhile is paired unwatched. Fix the label (Escape means back everywhere; the cancel is a row, like *Stop recording*), not Escape.
2. **`usb` on the selected USB entry clears the selection** (`wireless.py:527` `back_to_usb`). When the target is the USB serial itself and it is selected, the fallback list excludes it, `state.select(None)` runs and the hub says *No device* although the phone is still on the cable. Over IPC that is `usb ""` with the USB phone selected. Only a Wi-Fi target should move the selection.
3. **A queued `pair code` can be dropped without a word** (`Store.qml:195`). The panel blanks the field before `act(...)`, the job sits in `pendingRun` while the page's own `wireless` run is in flight (two adb calls, up to 10 s), and any further `run()` before that ends (`r`, a middle click, `page wireless` over IPC) replaces the queued job: no notice, no `onDone`, the six digits gone, the phone's dialog times out. Before 1.2.0 every queueable job was redoable from a visible row. Either queue more than one, or refuse to replace a job that carries stdin and say so.
4. **The wrong phone can be selected after a pair** (`wireless.py:299` `new_wifi_device`). When no ready entry is on the pairing host yet, the first new `wifi` entry on any host is taken; a second known phone whose Wireless debugging comes on during the window is selected and named. Filter by host: an `ip:port` serial by its host, an mDNS-named one by the host its connect service advertises (`attached_wifi_device` has that lookup since 1.3.1; share it).
5. **`go_wireless` can overrun the 60 s budget** (`wireless.py:513`). The retry deadline is checked after an attempt, so an attempt starting at 51 s runs a full 10 s connect plus the readiness wait, and the answer becomes the generic `timeout` instead of `The phone listens on ip:5555, but: …`; `state.select` never runs although `tcpip` succeeded. A packet-dropping LAN (the VPN case) makes every connect take its full 10 s. Check the deadline before starting an attempt, or size `TCPIP_WINDOW` against the remaining budget.
6. **A dead adb server reads as "this adb has no mDNS"** (`wireless.py:160` `mdns_available`). Any non-zero exit from `mdns check` returns `fmt.MDNS_MISSING_TEXT`, which tells the user to change `adbPath`, on the one adb that does have mDNS (seen on the `adb kill-server` dev-loop check). Only the `not supported` text should get that message; anything else is `adb_failed` with adb's own line. Related: `cmd_wireless`'s error path still calls `describe()` against the same broken adb (two more calls, up to 10 s) before the error document reaches the panel; pass `None` there.

Smaller, from the same review:

- **The countdown rebuilds the QR page every second** (`Panel.qml:646`). The seconds left are baked into the `rows` model, so the Repeater tears down and recreates every delegate per tick and the `Image` (`cache: false`, `Panel.qml:1395`) re-reads and re-decodes the PNG synchronously, 120 times a session. Bind the seconds in the delegate's `Text` instead and keep the row static; `asynchronous: true` for the one load.
- **`record` has the same early-cancel window `pair qr` had** (`cli.py:354` `cmd_record`): `ctx.device()` and the label lookup run before `capture.record` installs its handlers, so a `record stop` while the helper is still listing devices is dropped (the helper starts with SIGINT ignored). Arm the handlers from `dispatch` like `wireless.arm_cancel()`.
- **The pairing address is patched into the top stack entry** (`Panel.qml:1032` `pairaddr` → `setCurrent`). On the code step, Escape and Backspace pop the whole page to Wireless and the typed address is gone; a `push({ page: "paircode", addr })` would give the back step for free and make `setCurrent` unnecessary.
- **The `paired` envelope is emitted before the state is saved and carries no device list** (`cli.py:648`), unlike every other selection-changing answer (`_with_devices`). The tracker frame for the new device may be built from the old state file and briefly move the selection back. Save first and ride the fresh list; while at it, the `except OSError: pass` there swallows what `_finish` reports as `state_corrupt`.
- **`cmd_usb` resets `explicit_serial`** (`cli.py:553`), so a `--serial X usb Y` reports `selected` from the state instead of X. `explicit_serial` is also written by `_with_devices` and `_named_or_selected` as a side channel; `Context.device(serial=)`/`devices(selected=)` parameters would keep it read-only.
- **The pairer is a copy of the recorder** (`Service.qml:283` versus `175`): the same properties, `start/stop/toggle`, `apply*Line` guard, `Process` + 300 ms exit fallback, 1 s timer, IPC verb; they already drift (the recorder cannot tell "asked to stop" from "ended without an answer", the pairer can). One inline streaming-session component instantiated twice. Same family: three `apply*Line` parsers share eight lines, the three wireless renderers open with the same `adb not found` block that `deviceGate` already has, and a page name is spelled in eight enumerations in `Panel.qml`.
- **`refreshWireless` runs on the Pair with a code sub-page** (`Panel.qml`, `refresh()` and `enterPage`), which never reads `wirelessInfo`: two adb calls whose answer nobody looks at, and popping back runs them again. Drop `paircode` from both conditions. Related: one connect triggers three or four `wireless` re-reads (the `onDone` pop, then one per tracker frame); a 300 ms debounce like the APK folder box would do.
- **`mdns check` and `mdns services` run serially on every page paint** (`wireless.py` `describe`), though the first answer is a property of the adb binary. Remember it per `adb.path`, or run the two concurrently.
- **`new_wifi_device` / `attached_wifi_device` poll with labels** (`list_devices(adb)` default), one `emu avd name` per running emulator per 0.5 s poll; `with_labels=False` inside the loops, one labelled listing at the end.
- **`read_code`'s tty branch waits 60 s under a 60 s budget** (`wireless.py` `read_code`), so a terminal `pair code` with no digits typed answers `timeout` instead of the intended `bad_args`. A shorter tty wait, or disarm the alarm while waiting for a human.
- **`wireless.connect` is called with `state` by nobody** since 1.3.0 removed the recent addresses (it never was optional); `back_to_usb` takes `devices` and `state` separately while `cmd_usb` fetches the list only to hand it over and then rebuilds `devices` by hand instead of `_with_devices`. Small cleanups.
- Conventions: no hard violation. Two notes: the "Before the next session" section in `AGENTS.md` is future work by that file's own rule (this file or the plan's Status line is where it points), and `HOST_RE` lets an address reach 259 characters against the 256-character field rule.

## Helper details worth revisiting

- **Leftover recordings on the device.** A shell restart (or `omarchy plugin disable`) mid-recording SIGKILLs the recorder; PDEATHSIG ends the adb client, screenrecord finishes the file, and `/sdcard/omarchy-android-dev-<stamp>.mp4` stays there with nobody to pull it (seen 2026-09-05, the documented limitation). `record` or `status` could list `/sdcard/omarchy-android-dev-*.mp4` and offer a `Pull the leftover recordings` row, or the next `record` could pull them first.
- **`record stop` from a terminal.** The plan had a `record.json` with the recorder's pid and a `stop` verb signalling it; dropped in 0.4.0 because the invariant says no PID files. A terminal recording ends with Ctrl-C, the service's with the signal to its own Process. A `--time-limit N` argument (screenrecord's own; `0` lifts the limit on API 34+) would be the terminal-friendly way if one is ever wanted.
- **Which display a screenshot or a recording targets** on a foldable: `screencap -d` / `screenrecord --display-id` with the ids from `dumpsys SurfaceFlinger --display-id`; see the foldables note below.

- The `page` IPC verb opens the panel on the first registered bar widget when none is open; `open`/`toggle` go through the shell and pick the focused monitor. With two monitors `page` can open on the other one.

- **Foldables act weirdly; come back to them.** Seen on the `Pixel_10_Pro_Fold` AVD (android-37.2-beta3) on 2026-09-05: the emulator window draws the skin misaligned (the inner display over the frame's edge, the hinge along the bottom, a strip of the desktop showing through), `screencap -p` warns about multiple displays and picks the first, and the AVD reports two displays while unfolded. Development moved to the `Medium_Phone` AVD that day. To look at later: which display a screenshot and a recording should target (`-d <id>` from `dumpsys SurfaceFlinger --display-id`), whether the posture (`device_state`) matters to any command, and whether the skin problem is the emulator's or the AVD's.
- **The emulator window on Hyprland.** Checked 2026-09-05 with the `Medium_Phone` AVD, the answers are in `AGENTS.md` (the emulator is XWayland with a detached toolbar window; a `float` rule alone is enough, `center` is a no-op for it, the toolbar follows the floated main window). Dead ends: no launch flag sizes the window or hides the toolbar (`-qt-hide-window` hides everything, `-no-window` is headless), and the launcher rewrites `QT_SCALE_FACTOR` to `none`, so the plugin cannot scale the UI for a HiDPI monitor; the user resizes the window. Still open: an *Extra emulator arguments* setting like `scrcpyArgs`, mostly for `-gpu host` (the log here says `Your GPU drivers may have a bug. Switching to software rendering` on an NVIDIA card and picks swangle), once `-gpu host` is known to work under XWayland with that driver.
- `screencap -p` on a device with several displays (the foldable emulator) prints a warning ahead of the PNG and picks the first display; `-d <id>` would let the user choose. 1.0 strips the warning and keeps the image.
- A second `ps -A` format: some vendor ROMs print `ps` without the `u0_a` user column, so nothing shows as Running. A `pidof`-based fallback per listed package would be many calls; `dumpsys activity processes` is one.
- `resolve-activity` on packages with several launcher activities returns one; a picker would need `cmd package query-activities`.
